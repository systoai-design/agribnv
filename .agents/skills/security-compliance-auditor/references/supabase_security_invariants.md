# Supabase & PostgreSQL Security Invariants

This guide establishes the mandatory database security standards for UMANI's PostgreSQL backend and Supabase infrastructure.

---

## 1. Zero-Bypass Row Level Security (RLS)

### 1.1 Mandatory RLS on Every Table
* **Invariant:** Every single table created in schema `public` must immediately execute:
  ```sql
  ALTER TABLE public.<table_name> ENABLE ROW LEVEL SECURITY;
  ```
* **Failure State:** If RLS is not enabled, any unauthenticated or authenticated user with table permissions can perform arbitrary queries and mutations against all records.
* **Default Deny:** In PostgreSQL, enabling RLS without policies blocks all operations for non-superuser roles (`anon`, `authenticated`). Policies must selectively open access following the Principle of Least Privilege.

### 1.2 Policy Design & Performance
* **Index Foreign Keys Used in Policies:** Always index columns checked in RLS policies (e.g. `user_id`, `host_id`, `guest_id`, `property_id`). Missing indexes cause full table scans on every RLS evaluation.
* **Wrap `auth.uid()` in Subqueries:**
  * Suboptimal: `USING (auth.uid() = host_id)` (evaluates function per row)
  * Optimal: `USING ((SELECT auth.uid()) = host_id)` (evaluates once per query statement)
* **Avoid Circular Policy Recursion:** If Table A's policy queries Table B, and Table B's policy queries Table A, Postgres will abort with `infinite recursion detected in policy for relation`. Use dedicated `SECURITY DEFINER` lookup functions for cross-table permission checks.

## 2. Functions & Views Hardening

### 2.1 SECURITY DEFINER Function Invariants (CWE-426)
* A `SECURITY DEFINER` function executes with the privileges of the database owner rather than the calling user.
* **Mandatory Rule:** All `SECURITY DEFINER` functions MUST explicitly set a locked `search_path`:
  ```sql
  CREATE OR REPLACE FUNCTION public.check_user_permission(...)
  RETURNS BOOLEAN
  LANGUAGE plpgsql
  SECURITY DEFINER
  SET search_path = public, pg_temp
  AS $$
  BEGIN
    ...
  END;
  $$;
  ```
* **Exploit Vector:** Without `SET search_path`, a malicious user can create a malicious function or operator in a schema preceding `public` on the search path, hijacking execution when a privileged user calls the function.

### 2.2 Views and RLS Invocation (PostgreSQL 15+)
* By default in PostgreSQL, views execute with the privileges of the view owner, ignoring RLS policies on the underlying tables for the querying user.
* **Mandatory Rule:** All views exposing user or business data to client queries must include `WITH (security_invoker = true)`:
  ```sql
  CREATE OR REPLACE VIEW public.property_ratings
  WITH (security_invoker = true)
  AS SELECT
    property_id,
    ROUND(AVG(rating)::numeric, 1) as average_rating,
    COUNT(id) as review_count
  FROM public.reviews
  GROUP BY property_id;
  ```

## 3. Role Permissions & Grant Minimization

### 3.1 Avoid Blanket `GRANT ALL`
* Never execute blanket statements like:
  ```sql
  -- DANGEROUS PATTERN:
  GRANT ALL ON ALL TABLES IN SCHEMA public TO anon;
  ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT ALL ON TABLES TO anon;
  ```
* If a migration later creates an unshielded table without RLS, `anon` immediately gains full DROP, TRUNCATE, INSERT, and UPDATE power over that data.
* **Safe Pattern:** Only grant explicit `SELECT, INSERT, UPDATE, DELETE` to `authenticated`, and strictly `SELECT` (or specific INSERT) to `anon`.

## 4. Column-Level Security & PII Isolation

### 4.1 Profiles Table PII Leak Prevention
* The `public.profiles` table typically holds both public information (`full_name`, `avatar_url`, `bio`, `username`) and private PII (`phone`, `email`).
* **Vulnerability:** A policy `CREATE POLICY "Public Profiles" ON public.profiles FOR SELECT USING (true);` allows any unauthenticated bot to scrape the phone numbers and PII of every registered farmer and traveler.
* **Remediation Options:**
  1. Separate PII into a private table (`public.profile_private_info`) with strict `USING ((SELECT auth.uid()) = id)`.
  2. Create a secure public view `public.public_profiles` that excludes sensitive columns like `phone` and only expose that to `anon`.
  3. Enforce Postgres column-level security: `GRANT SELECT (id, full_name, avatar_url, bio, username) ON public.profiles TO anon;`.

## 5. Storage Bucket Security

### 5.1 Public vs Private Buckets
* Buckets containing public marketing images (farm photos, avatars, reels) are public read-only.
* Buckets containing legal waivers, host IDs (PhilSys, passports), sanitary permits, and booking receipts MUST BE PRIVATE.
* Private bucket files must only be accessed via short-lived signed URLs generated by authenticated Supabase client calls.
